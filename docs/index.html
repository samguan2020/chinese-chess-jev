How it works

The model never generates a move

A pure-Python rules engine enumerates every legal move. The model is asked exactly one choice question — pick the best move among these candidates — and returns a probability per option. No chain-of-thought, no illegal moves even representable.

Rules engine

Enumerates every legal move for the side to play; fully unit-tested, stdlib only.

Code-side judgment

Three small layers — repetition avoidance, material-trade weighting, hanging-piece defense — run before the model ever sees a candidate list.

One forward pass

The model scores the surviving candidates; the server applies the winner and checks for checkmate.

Training pipeline

Pikafish as the teacher, no human labeling

Self-play games sample positions; Pikafish (a free, GPL-licensed UCI engine) labels the best move at each one. --freeze-backbone keeps the 600M backbone out of the optimizer entirely — full fine-tuning needs ~9.6GB of AdamW state, confirmed by watching it OOM on this card.

Debugging a model with no lookahead

Three failure modes, found in real games, in this order

01 · Infinite piece-shuffling

A Knight moved back and forth between the same two squares for several turns

Undoing your own last move can look perfectly reasonable to a model with no memory of what it just did.

Fix: track the last 8 board positions and exclude any candidate that would recreate one — unless that leaves zero candidates, in which case the filter backs off rather than stalemate the AI by accident.

02 · Giving away material in trades the model doesn't evaluate

The AI traded its own Cannon for a Horse — a mild loss in real Xiangqi theory

The model has no explicit notion of piece value; it picks the capture that looks appealing in isolation.

Fix: one ply of material-only lookahead. Any capture that nets a loss gets its probability multiplied by 0.02 before the argmax — never driven to exactly zero, so a bad trade can still be played if it's genuinely the only option.

03 · Leaving a piece hanging — the real bug

A Cannon sat undefended for two full turns before the opponent simply took it

The first fix (a threat-penalty, mirroring the material fix above) didn't work. The reason was more interesting than the bug it was chasing: the defending move was never in the model's candidate list to begin with. With 40+ legal moves in the opening and a 12-move cap for GPU-memory reasons, a reweighting scheme can only rescue a candidate that's actually offered.

Real fix: move the guarantee one layer earlier — prune_moves() now always includes any move that resolves a currently-hanging piece, with the same priority as a capture. Verified by replaying the exact position that exposed the bug, and by a regression test that runs the "does the fix survive random sampling" check 20 times in a row, since the original bug was a matter of odds, not a hard failure.

What this project is actually testing

Code plans and enforces constraints; the model only makes narrow judgment calls

Why a decision model, not a chat model

Jev-style "System-1" models answer typed questions (yes/no, choice, rating) with a calibrated probability in one forward pass — no generation, no hallucinated illegal moves, no chain-of-thought to go wrong.

Why the Chinese text stays Chinese

The fine-tuned checkpoint was trained on Chinese board/move descriptions. Translating the model's input would silently shift it to a distribution it never trained on, on a checkpoint that already has very little data to spare. The UI translates for readability; the model's actual input doesn't change.

Why the backbone stays frozen

The obvious tradeoff: the backbone's understanding of text never adapts to what Xiangqi descriptions look like, capping how much the small head can learn from any amount of data — but it's the only option that fits a 4GB card.

What the GPU taught about trusting metrics

nvidia-smi's reported memory isn't the same as real risk — reserved memory crept toward 3.8GB while torch.cuda.max_memory_allocated(), the actual peak, stayed at 2.77GB the whole time. Per-question training cost also swung 3x depending on whether an idle inference server shared the card.
